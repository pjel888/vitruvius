# Vitruvius — System Architecture

## Purpose and Scope
Vitruvius is a structured knowledge extraction engine designed for processing Philippine building laws and regulations. It transforms raw sources (PDFs, Office documents, spreadsheets) into a canonical knowledge graph consisting of concepts and inter-document relationships.

## Current Architecture Summary
The system is built as a **layered, filesystem-centric pipeline**. It prioritizes file-system traceability over database persistence, using structured directories (001-006) to represent the lifecycle of a document from raw ingestion to canonical knowledge.

## Repository and Package Structure
The codebase follows a standard Python package structure, but keeps its core logic in `scripts/vitruvius` for ease of use in CLI-driven workflows.

### 1. Root Layers
- `001_Raw-Source-Layer/`: Entry point for all source documents.
- `002_Raw-Conversion-Layer/`: Intermediate artifacts (Markdown, Sidecar JSON) generated by the conversion subsystem.
- `003_Canonical-Knowledge-Layer/`: The refined knowledge base containing canonical source definitions and concept files.
- `004_Derived-Content-Layer/`: Downstream products (summaries, flashcards, explainers).
- `005_Operational-Intelligence-Layer/`: Caches, chunks, embeddings, and the graph storage (planned).
- `006_System-Manifests/`: Operational metadata (file registries, tree snapshots, and run logs).

### 2. Core Packages
- `scripts/`: CLI entrypoints and utility scripts.
  - `pipeline_cli.py`: The primary system orchestrator.
  - `vitruvius/`: The main functional package.
    - `scanner.py`, `status.py`: Ingestion and state tracking.
    - `conversion.py`, `ocr.py`, `office.py`, `spreadsheets.py`: Data transformation and OCR.
    - `canonicalize.py`, `concepts.py`: Mapping to the canonical knowledge layer.
    - `relationships.py`, `relationships_sections.py`: Link extraction logic.
    - `ollama_review.py`: LLM-based review and verification.
    - `paths.py`, `constants.py`: Filesystem contract enforcement.

## Runtime Entry Points
The system is invoked primarily through `scripts/pipeline_cli.py`.

- `python scripts/pipeline_cli.py run`: Full pipeline execution (Scan → Status → Lint).
- `python scripts/pipeline_cli.py convert`: Batch conversion of new/changed files.
- `python scripts/pipeline_cli.py canonicalize-one <rel_path>`: Canonicalizes a single markdown file.
- `python scripts/pipeline_cli.py extract-relationships-one <rel_path>`: Runs relationship extraction.
- `python scripts/pipeline_cli.py review-relationships-ollama`: Runs LLM-based review.

## Execution Flow
The system operates as a linear, idempotent pipeline:

1.  **Ingestion & Registry Update (`scan`):** Recursively crawls `001_Raw-Source-Layer` and updates the file registry in `006_System-Manifests/registries`.
2.  **Status Check (`status`):** Compares the filesystem against the registry to identify new or changed files.
3.  **Conversion Layer (`convert`):**
    - Converts PDFs using `opendataloader_pdf`.
    - Converts Office files using `office.py`.
    - Detects scanned PDFs and routes them through the OCR subsystem (`ocr.py`).
    - Generates Markdown and JSON sidecars in `002_Raw-Conversion-Layer`.
4.  **Canonicalization (`canonicalize`):**
    - Matches files against `rules/canonical_rules.yaml`.
    - Assigns stable, prefixed IDs (e.g., `law-national-building-code`).
    - Creates or updates files in `003_Canonical-Knowledge-Layer`.
5.  **Relationship Extraction (`relationships`):**
    - Scans canonical markdown using regex patterns and a concept map.
    - Generates extraction reports in `006_System-Manifests/runs`.
6.  **Verification (`review`):**
    - Submits extracted relationships to a local LLM (Ollama) for validation.

## Subsystem Architecture

### 1. Ingestion Subsystem
**Components:** `scanner.py`, `status.py`, `reconcile.py`.
**Responsibility:** Ensures the filesystem is indexed and consistent. It produces registries (`.csv`) and snapshots (`.json`) to track state across runs.

### 2. Conversion Subsystem
**Components:** `conversion.py`, `detection.py`, `ocr.py`, `office.py`, `spreadsheets.py`.
**Responsibility:** Transforms diverse source formats into a standard "Raw Markdown" format. It includes logic for identifying OCR requirements and managing Office-to-PDF workflows.

### 3. Canonicalization Subsystem
**Components:** `canonicalize.py`, `concepts.py`.
**Responsibility:** Enforces the "Strict ID System". It uses a declarative rules engine to map paths to canonical entities.

### 4. Extraction Subsystem
**Components:** `relationships.py`, `relationships_sections.py`.
**Responsibility:** Pattern-based extraction of relationships (e.g., `requires`, `defines`, `depends_on`). It is "concept-aware," using files in `003_Canonical-Knowledge-Layer/shared/concepts` as its vocabulary.

### 5. Review Subsystem
**Components:** `ollama_review.py`.
**Responsibility:** Provides an LLM-based second pass for verification, ensuring that the pattern-based extractions are semantically valid.

## Filesystem and Artifact Architecture
The system uses a **path-based addressing scheme**.
- Markdown output: `top_category/raw_markdown/nested_parts/filename.md`
- JSON output: `top_category/sidecar_json/nested_parts/filename.json`
- This ensures that artifacts for `001-Laws/PD-1096.pdf` are always found in predictable locations.

## Data and Document Flow
1.  **Source:** `001_Raw-Source-Layer/001-Laws/PD-1096.pdf`
2.  **Conversion:** `002_Raw-Conversion-Layer/001-Laws/raw_markdown/PD-1096.md`
3.  **Canonical:** `003_Canonical-Knowledge-Layer/shared/sources/national-building-code.md` (metadata with ID `law-national-building-code`)
4.  **Relationships:** `006_System-Manifests/runs/latest_relationship_extraction.json`

## Rules, Config, and Registry Layer
- `scripts/vitruvius/rules/canonical_rules.yaml`: The primary brain for entity classification.
- `config/vitruvius.yaml`: System-wide configuration.
- `006_System-Manifests/registries/`: CSV files acting as the system's "database".

## Implemented vs Planned Architecture
- **Implemented:** All layers from Ingestion through Relationship Extraction and LLM Review are present and functional. The filesystem-driven registry system is the source of truth.
- **Planned (Roadmap):** 
  - Graph Database integration (Neo4j or similar) in `005`.
  - Advanced chunking and embedding pipelines for RAG.
  - Multi-parser strategy for complex document layouts.

## Architectural Risks and Weaknesses
- **Tight Coupling to Filesystem:** Relies heavily on directory structure. Renaming folders can break the registry.
- **Regex-Based Extraction:** Initial extraction is fragile and sensitive to document formatting.
- **Ollama Dependency:** Review layer requires an active Ollama server and specific models (e.g., `gemma4:31b`).

## Verified Claims

## KV Storage Backends (Sprint HP.3-R, 2026-04-15)

The two persistent KV stores in the project now ship with parallel
RocksDB backends alongside the original SQLite implementations.

| Module | SQLite class | RocksDB class | Flag |
|---|---|---|---|
| `scripts/vitruvius/graph/event_store.py` | `EventStore` | `scripts/vitruvius/graph/rocksdb_event_store.py::RocksDBEventStore` | `hp_rocksdb_event_store` |
| `scripts/vitruvius/review/stateful_registry.py` | `StatefulReviewRegistry` | `scripts/vitruvius/review/rocksdb_stateful_registry.py::RocksDBStatefulReviewRegistry` | `hp_rocksdb_verdict_cache` |

Consumers go through factory functions that dispatch on the flag:

- `make_event_store(*, db_path)` in `scripts/vitruvius/graph/event_store.py`
- `make_stateful_registry(*, db_path)` in `scripts/vitruvius/review/stateful_registry.py`

Both flags default to **true** as of AD-029 (2026-04-15). The
flag-OFF SQLite path is retained as a fallback. Operators who need
to roll back can set either flag to `false` in
`config/vitruvius.yaml`.

**Migration tool:** `ple-kv-migrate --store {event,registry} --source SQLITE_FILE --dest ROCKSDB_DIR [--dry-run]`
copies existing SQLite state into a fresh RocksDB directory.
Idempotent (safe to re-run).

**Binding:** `rocksdict 0.3.29` — modern Rust-based Python binding.
NOT `python-rocksdb` (the Cython-based binding that was originally
unavailable on Apple Silicon Python 3.11 and caused the Sprint HP
pivot to SQLite).

**Bench (n=10000, AD-029):**
- Event store: RocksDB 18.7× faster than SQLite
- Verdict cache: RocksDB 24.3× faster than SQLite

See AD-029 in `/.ai/10_state/decisions.md` for the full bench ledger
and the O(1) `count()` optimization story.

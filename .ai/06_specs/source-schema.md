# Source Schema — Canonical Source Files

> **Applies to:** files under `003_Canonical-Knowledge-Layer/shared/sources/` and `003_Canonical-Knowledge-Layer/<category>/` representing a primary or secondary source document.
> **Authoritative roadmap reference:** `/.ai/01_roadmap/master-roadmap.md` §2, §3
> **Schema version:** `1.0.0`
> **Updated:** 2026-04-14

---

## 1. Purpose
A Source represents a real-world document (law, regulation, standard, handout, reviewer) admitted into the Vitruvius canonical layer. Sources anchor every relationship, concept, and evidence snippet downstream. A source record exists in two coordinated forms:

1. **A Markdown file** with YAML frontmatter in `003_Canonical-Knowledge-Layer/shared/sources/<slug>.md`.
2. **A lineage trail** from the raw document (`001_Raw-Source-Layer/.../<file>.pdf`) through the refinement manifest (planned Phase 1C) through this canonical record.

## 2. File Location & Naming
- **Directory:** `003_Canonical-Knowledge-Layer/shared/sources/`
- **Filename:** `<slug>.md` — lowercase, hyphen-separated, URL-safe.
  - Example: `national-building-code-of-the-philippines.md`
- **ID prefix:** `law-`, `irr-`, `source-`, `handout-`, `reviewer-`.
  - See `/.ai/00_system/naming-conventions.md` for the full prefix list.

## 3. Frontmatter — Required Fields
Every source file MUST include the following YAML frontmatter keys.

| Field | Type | Description |
|---|---|---|
| `id` | string | Canonical ID, `<prefix>-<slug>`. Immutable once written. |
| `title` | string | Human-readable title. |
| `page_type` | enum | Literal: `source`. |
| `trust_level` | enum | `primary` \| `secondary` \| `tertiary` \| `unverified`. |
| `canonical_status` | enum | `draft` \| `enriched` \| `verified` \| `superseded`. |
| `last_canonicalized_utc` | ISO-8601 UTC string | Last time the file was regenerated. |

### 3.1 Trust Level Definitions
- **`primary`** — Official government gazette text, authoritative promulgation.
- **`secondary`** — Official IRR, department orders, authoritative commentary.
- **`tertiary`** — Reputable third-party commentary, textbooks.
- **`unverified`** — Source has not been vetted; relationships from this source cannot be promoted.

### 3.2 Canonical Status Lifecycle
```
draft ─► enriched ─► verified ─┐
   ▲                           │
   └───── superseded ◄─────────┘
```
- `draft` — Generated by `canonicalize.py`; no manual review.
- `enriched` — Structured sections populated (Overview, Coverage, Key Points, Referenced Concepts).
- `verified` — Reviewed by a domain expert OR all extracted relationships from this source have cleared the Promotion Gate.
- `superseded` — Replaced by a newer version. Retained for history. Not consumed by extraction.

## 4. Frontmatter — Optional Fields
| Field | Type | Purpose |
|---|---|---|
| `aliases` | string[] | Alternate names. Used by extraction and alias registry (Phase 1C §10). |
| `category` | string | Top-level source category (e.g., `001-Laws`). |
| `topic_tags` | string[] | Domain tags for filtering. |
| `source_documents` | string[] | Relative paths to raw files under `001_Raw-Source-Layer/`. |
| `source_artifacts` | string[] | Relative paths to the refined Markdown under `002_Raw-Conversion-Layer/`. |
| `jurisdiction` | string | e.g., `philippines`. |
| `effective_date` | ISO-8601 date | When the source took legal effect. |
| `supersedes` | string[] | IDs of source documents this record replaces. |
| `superseded_by` | string | ID of the newer source, if any. |
| `language` | string | ISO 639-1 (e.g., `en`, `fil`). |

## 5. Body Structure — Required Sections
The Markdown body MUST include the following H2 sections in order. Phase 2 canonicalizer restoration is responsible for generating them.

### 5.1 `## Overview`
One paragraph describing the source's purpose and scope. Written for a domain-aware reader.

### 5.2 `## Coverage`
Bulleted list of the topical areas or sections the source covers. Each item links to concepts where a match exists.

### 5.3 `## Key Points`
3–8 bulleted key provisions or requirements. Each item should be attributable to a specific section of the source.

### 5.4 `## Referenced Concepts`
Bulleted list of concept IDs referenced by this source. Each entry is a canonical concept ID like `concept-occupancy-classification`.

### 5.5 `## Related Concepts` *(legacy, now aliased to Referenced Concepts)*
Older files may use `## Related Concepts` instead. The canonicalizer treats both as equivalent during reads; writes use `## Referenced Concepts`.

## 6. Body Structure — Optional Sections
- `## Historical Context` — Why the source was enacted.
- `## Supersession History` — Table of ancestor documents with effective dates.
- `## External References` — Links to official gazettes, publication records.
- `## Notes` — Free-form commentary. Not consumed by extraction.

## 7. Worked Example
```markdown
---
id: law-national-building-code-of-the-philippines
title: National Building Code of the Philippines
page_type: source
trust_level: primary
canonical_status: enriched
last_canonicalized_utc: 2026-04-14T02:49:00Z
aliases:
  - PD 1096
  - Presidential Decree No. 1096
  - National Building Code
category: 001-Laws
topic_tags:
  - building-code
  - philippines
jurisdiction: philippines
effective_date: 1977-02-19
language: en
source_documents:
  - 001-Laws/PD-1096/PD 1096 - National Building Code of the Philippines.pdf
source_artifacts:
  - 002_Raw-Conversion-Layer/001-Laws/raw_markdown/PD-1096/PD 1096 - National Building Code.md
---

# National Building Code of the Philippines

## Overview
Presidential Decree No. 1096, the National Building Code of the Philippines,
establishes a uniform set of standards for the design, construction, occupancy,
and maintenance of buildings across the Republic…

## Coverage
- Occupancy classification
- Fire-resistive construction requirements
- Light and ventilation standards
- Building permit procedures

## Key Points
- Every building must be classified by occupancy type.
- Fire-resistive requirements scale with occupancy risk.
- Certificates of Occupancy are required before use.

## Referenced Concepts
- concept-occupancy-classification
- concept-building-permit
- concept-certificate-of-occupancy
- concept-fire-resistive-construction
- concept-light-and-ventilation
```

## 8. Validation Rules
These rules MUST be enforced by the canonicalizer and by `run_lint`.

1. **Frontmatter present.** File starts with `---` and has a closing `---`.
2. **Required fields present.** `id`, `title`, `page_type`, `trust_level`, `canonical_status`, `last_canonicalized_utc`.
3. **ID format.** Matches `^[a-z][a-z0-9-]*$` with a valid prefix.
4. **`page_type == "source"`.**
5. **`trust_level` in allowed enum.**
6. **`canonical_status` in allowed enum.**
7. **`last_canonicalized_utc` parseable as ISO-8601 UTC.**
8. **No duplicate IDs** across `003_Canonical-Knowledge-Layer/`.
9. **Required body sections** present when `canonical_status != "draft"`.
10. **Referenced concepts exist.** Every concept ID in `## Referenced Concepts` must resolve to a file under `003_Canonical-Knowledge-Layer/shared/concepts/`.

## 9. Relationship to Other Schemas
- **Concept schema** (`concept-schema.md`): Every entry in `## Referenced Concepts` is validated against the concept schema.
- **Relationship schema** (`relationship-schema.md`): Every relationship record references at least one source by ID; sources provide the `source_section_id` and `evidence_snippet` values.

## 10. Change Policy
- **`id` is immutable.** Changing an ID requires `migrate-ids-plan` → `migrate-ids-apply`.
- **`trust_level` downgrades** (e.g., `primary` → `unverified`) automatically flag all dependent relationships for re-verification.
- **`canonical_status` transitions** are the canonicalizer's responsibility. Manual edits to the body are preserved if `canonical_status == "enriched"` or `"verified"` (protected by diff-before-write — Phase 2 restoration).

## 11. Open Questions
- Whether `trust_level: unverified` sources should be readable by the extractor at all. Current position: yes, but no relationship extracted from them can be promoted (the Promotion Validator rejects them).
- Whether `supersedes` / `superseded_by` links should generate automatic `supersedes` predicate edges. Deferred until Phase 7 Promotion Layer ships.
